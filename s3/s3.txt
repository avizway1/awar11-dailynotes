Storage Types : 
Block Based Storage : We can attach to instance, we can run OS.. Install programs.. : EBS 
Storage over network / Shared Storage : EFS
Object Based Storage : Everything stores as a object / flat file. We cannot install any OS, run any application : S3



S3 : simple storage service. 

--> We can store all flat files. 
--> We have to create a bucket to store the object. The object can be anything. 

Bucket = folder / Directory with unique namespace.
Object = Whatever we store inside a bucket, we call it as a object.

General purpose Bucket : it's a traditional S3 bucket for storing objects like files, images, backups, videos, and audios. Data spans across Multi AZs.

Directory Bucket : a special bucket designed for S3 Express One Zone, providing low latency for single-availability-zone applications. Data stores only in 1 AZ.

Table Bucket : table buckets designed for storing Apache Iceberg tables. We can use this table for analytical purposes. 

vector Bucket : the purpose of a vector bucket is for storing and querying vector embeddings with vector indexes and similarity search APIs. AI/ML - RAG, semantic Search.. 

Similar meaning --> Nearby Vectors
Different Meaning --> Distant vector

S3 Storage Classes : 

S3 Standard : designed for frequently accessed data with millisecond access.
- We can access data without any delays.
- Data spans across multiple availability zones (>= 3 AZs)
- 99.99% Availability.. 99.999999999% Durability..

Standard-IA (Infrequently Accessed) : designed to store less frequently accessed data. 
- We can access data  without any delays.
- Data spans across multiple availability zones (>= 3 AZs)
- 99.99% Availability.. 99.999999999% Durability..

OneZone-IA (Infrequently Accessed) : designed to store less frequently accessed data. 
- We can access data without any delays.
- Data store only in 1 availability zones (1 AZs)
- 99.95% Availability.. 99.999999999% Durability..

Glacier Instant Archieve :
--> Long-lived archive data access once a quarter with instant retrieval in milliseconds. 

Glacier Flexible Retrieval : 
- Long-lived archive data accessed once a year with Retrieval time 2 to 5 hours. 
- We cannot access data immediately. 
- We need to initialise the data restoration to view the object. 

Glacier Deep Archieve : 
- Long-lived archive data accessed once a year with Retrieval time 12 to 24 hours. 
- We cannot access data immediately.
- We need to initialise the data restoration to view the object. 

Data Retrival Options:
Bulk Retrival : data retried typically within 5 to 12 hours. 
Standard Retrival : data retried typically within 3 to 5 hours. 
Expedited Retrival : data retried typically within 1 to 5 minutes, Max obj size is 250 MB. 


RRS : reduced redundant storage : "not recommended" as durability is just 99.99% and cost is more than standard. 

Intelligent tiering : we can store data with changing or unknown access patterns.

Versioning : versioning helps to maintain multiple copies of our object within the same bucket. 
- By default versioning will be in a suspended state. 
- Existing objects won't have any version ID. After enabling versioning all uploads will get a version ID. We cannot manage or edit this ID. 

- If any override happens we can delete one particular version to get our object to a proper state. 
- If any object is deleted accidentally (Versioning = hide state), we will get a delete marker. Delete the delete marker to get the object back. 


Permanently delete : Object is Gone, No way to get the object back.
Delete : We will get a delete marker, Delete the delete marker to get the object back.

----

Problem 1 : when we enable versioning and start using versioning, for every edit we will get a version and obviously this will incur more cost. 

Problem 2 : we have some data. We are going to access the data 
- frequently for the first 30 days, 
- less frequently for 30 to 90 days.
- As a compliance requirement, we need to store the data for at least 3 years and 
- after 3 years it needs to be deleted automatically. 

Solution : 
life cycle management role / LCR : LCR helps to transition an object from one storage class to another storage class based on the defined days. Also we can configure to Delete an object at a particular time. 

- We can apply a particular transition configuration for current versioned objects and 
- another set of configuration for non-current versioned objects. 
- We do have an option to apply retention for the most recent copies.

Encryption is the process of converting human-readable data into unreadable or cypher/scrambled text to protect its privacy and security. 

Plaintext: The original readable information
Ciphertext: the scrambled, unreadable data
Cryptographic Keys : a special digital code or mathematical value used to lock (encrypt) and unlock (decrypt) the information back into readable form 

Symmetric encryption : use the exact same key for encryption and decrypting the data. 
Asymmetric encryption : uses a pair of keys: a public key to lock/encryption the message and a private key to unlock/decryption it. 


encode : scrambled text is fixed.
encrypt : scrambled text will/can be change.


--

In-Transit Encryption / At-Flight Encryption : when the data is in the travel state to the S3 platform, data will be encrypted, similar to websites with the HTTPS protocol (SSL or TLS certificate).  

Client Side Encryption / CSE : before uploading data to the S3 platform, we can use our own encryption method and we can encrypt the data. This is purely the customer's responsibility. 

Server Side Encryption / SSE : when data is in the S3 platform, we can apply our required encryption method. We have multiple options here. 


Server Side Encryption with S3 managed keys (SSE-S3) : default encryption method..
- S3 Generates and Manages the key material.
- Whoever has access to the S3 platform can decrypt the data. No additional permissions required. 
- We "can make data public" using only this particular key type. 
- No direct access to key material. We cannot view/alter/delete/rotate the keys. 

---

SSE - KMS (Key Management Service) - DMK (Default Master Key)
- KMS Service Generates and Manages the key material.
- Whoever has access to the S3 platform can decrypt the data. No additional permissions required. 
- No direct access to key material. We cannot view/alter/delete/rotate the keys. 
- This key is created automatically whenever we start using any of the services. 
- We cannot make objects public. 

---

SSE - KMS (Key Management Service) - CMK (Customer Master Key)
- Customer has to Create the KMS Key... KMS Service Manages the key material.. 
- User should have S3 Access first.. User/role should have permissions on KMS Key as well (usage permissions).
- No direct access to key material. We can rotate the key material.  
- We cannot make objects public. 

---

SSE - KMS (Key Management Service) - C (Customer provided Key)
- Customer has to Create and Manages his own key and ...  We need to upload the Key to KMS Service.. 
- User should have S3 Access first.. User/role should have permissions on KMS Key as well (usage permissions).
- Customer is responsible for key material and he can rotate the key material based his requirement.  
- We cannot make objects public.
