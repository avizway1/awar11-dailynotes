One interview point worth adding: Multi-AZ DB instance uses synchronous replication, while Multi-AZ DB cluster uses semi-synchronous replication. Semi-sync means a write is confirmed once at least one reader acknowledges it, which is why the cluster gets faster commits and faster failover.

Read Replica : 

We get another copy of our DB, We can choose required configuration for Replica.
--> Replicas support only read only operations.
--> If required we can create replica copy in another AZ / Another Region. 
--> When we perform write operation to WRITER/PRIMARY DB, It replicates to Replica without delays. 
--> We can promote replica to primary copy. Its irreversable process. 

==> We have an BI Application, that need to scan our entire DB to generate the report. When the scan is happening, your DB is facing perfarmance issues. How you design a solution to fix the DB perm issue..? 

Ans: create a read replica and point the BI application to Read Replica to generate the report. Based on load, we cna adjust the read replicas configuration.

Amazon Aurora : Its AWS Own Database Engine..
It has two compatible editions:
1. MySQL compatible
2. PostgreSQL compatible

Aurora also has a serverless option. We can configure minimum and maximum ACUs based on the load. We measure the configuration by using ACU (Aurora Capacity Unit). 
--> 1 ACU provides 2 GB of memory. 

--> Most of the other databases support a maximum storage of 64 TB only but Amazon Aurora supports up to 128 TB. 

--> Aurora gives 5x better performance at lower cost than other enterprise databases. 

--> Six-way replication across three Availability Zones
--> Up to 15 read replicas with replica lag under 10-ms
--> Automatic monitoring with failover


We dont have option to disable the backup on Aurora
Min : 1 Day for Aurora (other DB: We can turn off this feature)
Max : 35 Days (For all DBs)

Ans : we can adjust the "parameter group" associated with the RDS instance to adjust any of the MySQL configuration settings.

Snapshot : a snapshot is nothing but a backup copy of our database. A snapshot happens based on two things:
1. the backup window we configured on our DB cluster
2. whenever we are performing any major modifications on our database, Atlas automatically takes a snapshot.

3. We always have option to create a snapshot manually.


---

We have 2 options to restore our Database.

1. Snapshot (Use latest snapshot and restore the DB) 
2. PITR : Point In Time Recovery : AWS automatically backups data, we can choose the time frame to get a new copy of our DB.
