Serve the To-Do app with nginx, DynamoDB and EFS

One container image. Nginx serves the website out of an EFS file system mounted at /usr/share/nginx/html and reverse-proxies /api/ to the Node API, which keeps every task in an Amazon DynamoDB table. Content lives on EFS, data lives in DynamoDB, and the container itself keeps nothing.

DynamoDB table
Tasks
Partition key
id · String
Sort key
none
EFS mount
/usr/share/nginx/html

    The two things you will be asked in the viva

    QuestionAnswer
    DynamoDB table nameTasks
    Primary key (partition key)id — type String (S)
    Sort keynone — the key is the partition key alone
    Capacity modeOn-demand (PAY_PER_REQUEST)
    Who generates the keythe app — randomUUID() in server.js
    Other attributestitle, description, dueDate, status, createdAt
    Why only the key is declared

    DynamoDB is schemaless: the table definition declares the key and nothing else. title, dueDate and the rest are simply written with each item, which is why the create-table command below lists one attribute and no columns.

    Before you start

    Run it on your laptop first

    Ten minutes here saves an hour of ECS debugging. The compose file starts the same image against DynamoDB Local, with a Docker volume standing in for EFS at exactly the same path.

    docker compose up --build

    Open http://localhost:8080, add a task, then confirm each layer separately:

    # nginx is alive (never touches the API or the database)
curl -i http://localhost:8080/healthz

# the proxy and the API behind it
curl -s http://localhost:8080/api/tasks | head -c 400

# the website really is being served off the volume, not the image
docker compose exec frontend ls -la /usr/share/nginx/html
    What good looks like

    /healthz returns 200 ok, /api/tasks returns a JSON array, and the ls shows index.html, script.js, style.css and images/ owned by nginx.

    The runbook

    1

    Create the DynamoDB table

    The one piece of state that AWS keeps for you. Do it first — the task role in step 8 points at this table's ARN.

    DynamoDB›Tables›Create table
    FieldValue
    Table nameTasks
    Partition keyid
    Partition key typeString
    Sort keyleave empty
    Table settingsDefault settings
    Capacity modeOn-demand

    Or from the CLI:

    aws dynamodb create-table \
  --region ap-south-1 \
  --table-name Tasks \
  --attribute-definitions AttributeName=id,AttributeType=S \
  --key-schema AttributeName=id,KeyType=HASH \
  --billing-mode PAY_PER_REQUEST
    aws dynamodb wait table-exists --region ap-south-1 --table-name Tasks
    Name and key must match the app

    server.js reads the table name from DDB_TABLE (default Tasks) and addresses every item by { id }. Change the name here and you must change the environment variable in step 10 and the ARN in step 8. The key attribute id is not configurable — it is written into the code.

    3

    Build and push the image

    The only step that is not console clicking.

    aws ecr get-login-password --region ap-south-1 \
  | docker login --username AWS \
    --password-stdin 111122223333.dkr.ecr.ap-south-1.amazonaws.com
    docker buildx build --platform linux/amd64 --push \
  -t 111122223333.dkr.ecr.ap-south-1.amazonaws.com/todo-nginx:latest .
    Do not use the console's plain docker build

    On an Apple Silicon Mac it produces an arm64 image and Fargate defaults to x86. The task then fails with image Manifest does not contain descriptor matching platform. --platform linux/amd64 is what prevents it.

    Confirm what you pushed actually runs before going near ECS:

    docker run --rm -p 8080:80 \
  -e AWS_REGION=ap-south-1 -e DDB_TABLE=Tasks \
  111122223333.dkr.ecr.ap-south-1.amazonaws.com/todo-nginx:latest

    The page loads from the image's own copy of the site. The task list will be empty or error unless your shell's credentials reach the table — that part is what the task role fixes in step 8.

    4

    Create two security groups

    Order matters: the second one refers to the first.

    EC2›Security Groups›Create security group

    First — the group the task runs in:

    FieldValue
    Nametodo-task-sg
    VPCyour VPC
    Inbound ruleHTTP · port 80 · source 0.0.0.0/0
    Outboundleave the default allow-all

    Second — the group on the EFS mount targets:

    FieldValue
    Nametodo-efs-sg
    VPCthe same VPC
    Inbound ruleNFS · port 2049 · source todo-task-sg
    The single most common EFS failure

    Source on that 2049 rule must be the task security group, not a CIDR and not 0.0.0.0/0. Get it wrong and the task never starts: it sits in PROVISIONING and then dies with ResourceInitializationError: failed to invoke EFS utils.

    Port 3000 appears in no security group anywhere. The API is reachable only from nginx inside the same container.

    5

    Create the EFS file system

    Where the website lives. It outlives every task you will ever run.

    EFS›File systems›Create file system›Customize
    FieldValue
    Nametodo-web
    Storage classRegional
    Throughput modeElastic
    Encryption at restEnabled
    Mount targetsone in each subnet the task will use
    Mount target security grouptodo-efs-sg (remove the default group)

    Copy the file system ID — it looks like fs-0a1b2c3d4e5f6a7b8.

    A mount target per Availability Zone

    A task can only mount EFS through a mount target in its own AZ. Two subnets in the service means two mount targets, or the task fails in whichever AZ you missed — intermittently, which is worse than failing every time.

    6

    Create the EFS access point

    This is what makes the files readable by nginx. Get the UID wrong and you get 403s on every page.

    EFS›File systems›todo-web›Access points›Create access point
    FieldValue
    Nametodo-web-ap
    Root directory path/site
    POSIX user — User ID101
    POSIX user — Group ID101
    Root creation — Owner user ID101
    Root creation — Owner group ID101
    Root creation — Permissions0755
    aws efs create-access-point \
  --region ap-south-1 \
  --file-system-id fs-0a1b2c3d4e5f6a7b8 \
  --posix-user Uid=101,Gid=101 \
  --root-directory 'Path=/site,CreationInfo={OwnerUid=101,OwnerGid=101,Permissions=0755}' \
  --tags Key=Name,Value=todo-web-ap
    Why 101 and not 1000

    An access point squashes every file operation to one POSIX user. In the official nginx image the worker processes run as the nginx user, which is uid 101, gid 101. Any other value and nginx cannot read its own document root: the browser gets 403 Forbidden and the log says Permission denied while the files are plainly there.

    Copy the access point ID — fsap-0a1b2c3d4e5f6a7b8.

    7

    Create the log group

    Create it yourself so the first failed task has somewhere to write.

    CloudWatch›Log groups›Create log group
    aws logs create-log-group --region ap-south-1 --log-group-name /ecs/todo-nginx
    aws logs put-retention-policy --region ap-south-1 \
  --log-group-name /ecs/todo-nginx --retention-in-days 7

    Both processes log to stdout, so this one group carries the nginx access log, the nginx error log and everything server.js prints.

    8

    Create the two IAM roles

    One role for the ECS agent, one for your code. They are not interchangeable.

    Execution role — used by the ECS agent

    Pulls the image from ECR and writes to CloudWatch Logs. If ecsTaskExecutionRole already exists in your account, reuse it.

    IAM›Roles›Create role›AWS service›Elastic Container Service Task
    FieldValue
    Trusted entityecs-tasks.amazonaws.com
    Permissions policyAmazonECSTaskExecutionRolePolicy
    Role nameecsTaskExecutionRole

    Task role — used by server.js

    Same trusted entity, but the policy below. This is the credential the AWS SDK picks up inside the container.

    FieldValue
    Trusted entityecs-tasks.amazonaws.com
    Permissionsinline policy, below
    Role nametodo-task-role
    {
  "Version": "2012-10-17",
  "Statement": [
    {
      "Sid": "TasksTableAccess",
      "Effect": "Allow",
      "Action": [
        "dynamodb:DescribeTable",
        "dynamodb:Scan",
        "dynamodb:GetItem",
        "dynamodb:PutItem",
        "dynamodb:UpdateItem",
        "dynamodb:DeleteItem"
      ],
      "Resource": "arn:aws:dynamodb:ap-south-1:111122223333:table/Tasks"
    }
  ]
}
    Those six actions, and why

    DescribeTable is the startup check; Scan backs the task list and its filters; the other four are add, edit, tick and delete. Nothing else is needed — the resource ARN names one table, so this role cannot touch anything else in DynamoDB.

    If you would rather let the app create the table on first boot instead of doing step 1, add dynamodb:CreateTable. With the table already there, server.js returns straight after DescribeTable and never calls it.

    aws ecs register-task-definition --region ap-south-1 --cli-input-json file://taskdef.json
    Never set DDB_ENDPOINT here

    DDB_ENDPOINT is the local-development switch. Set it and the SDK talks to that address instead of the real service — on ECS that means the app quietly fails to reach a database that is not there. Leave it out and the SDK uses the managed DynamoDB service with the task role's credentials.

    Doing this in the console instead

    ECS › Task definitions › Create new task definition. The EFS volume is under Storage › Add volume › type EFS: pick the file system, set Access point to todo-web-ap, turn Transit encryption on, then add a mount point on the container with container path /usr/share/nginx/html.

    If you switch the access point to IAM authorization

    Setting "iam": "ENABLED" makes EFS check the task role too. Add elasticfilesystem:ClientMount and elasticfilesystem:ClientWrite on the file system ARN to todo-task-role, or the mount is refused.

    Create the service

    One task, kept running, replaced when it dies.

    ECS›todo-nginx-cluster›Services›Create
    FieldValue
    Compute optionsLaunch type · FARGATE · platform 1.4.0 or LATEST
    Task definitiontodo-nginx · latest revision
    Service nametodo-nginx-service
    Desired tasks1
    Subnetsyour two public subnets
    Security grouptodo-task-sg
    Public IPTurned on
    aws ecs create-service --region ap-south-1 \
  --cluster todo-nginx-cluster \
  --service-name todo-nginx-service \
  --task-definition todo-nginx \
  --desired-count 1 \
  --launch-type FARGATE \
  --platform-version 1.4.0 \
  --network-configuration 'awsvpcConfiguration={subnets=[subnet-aaaaaaaa,subnet-bbbbbbbb],securityGroups=[sg-tasktasktask],assignPublicIp=ENABLED}'
    Public IP must be on

    In a public subnet there is no NAT gateway, so a task without a public IP cannot reach ECR to pull the image. The symptom is CannotPullContainerError with a timeout.

    EFS needs Fargate platform version 1.4.0 or later. LATEST satisfies that.

    12

    Open it and prove both layers

    The point of the exercise: content on EFS, data in DynamoDB, nothing in the container.

    Find the public IP — ECS › cluster › Tasks › the running task › Public IP, or:

    aws ecs describe-tasks --region ap-south-1 \
  --cluster todo-nginx-cluster \
  --tasks $(aws ecs list-tasks --region ap-south-1 --cluster todo-nginx-cluster --query 'taskArns[0]' --output text) \
  --query 'tasks[0].attachments[0].details[?name==`networkInterfaceId`].value' --output text \
  | xargs -I {} aws ec2 describe-network-interfaces --region ap-south-1 \
      --network-interface-ids {} \
      --query 'NetworkInterfaces[0].Association.PublicIp' --output text

    Browse to http://<that-ip>/ — port 80, no port number needed. Then:

    1. Add a task in the UI.
    2. Open DynamoDB › Tables › Tasks › Explore items. Your task is there, keyed by a UUID in id.
    3. Stop the running task in the ECS console. The service starts a replacement with a new public IP.
    4. Open the new IP. The website is still there (EFS) and so is your task (DynamoDB).
    What you just demonstrated

    The container was destroyed and rebuilt and lost nothing, because it stored nothing. That is the whole argument for keeping content on EFS and records in DynamoDB.

    Follow the logs while you do it:

    aws logs tail /ecs/todo-nginx --region ap-south-1 --follow

    On a healthy first boot you will see [entrypoint] /usr/share/nginx/html is empty - seeding it from /opt/app/site, then the API line, then nginx access logs. On every boot after that the web root is no longer empty and the seeding is skipped.

    13

    Change the website without rebuilding the image

    The reason the content is on EFS in the first place.

    Option A — ship a new UI with the image

    Build and push as in step 3, set SEED_WEB_ROOT to always in the task definition, and redeploy. Every start then overwrites the web root with the image's copy.

    aws ecs update-service --region ap-south-1 \
  --cluster todo-nginx-cluster \
  --service todo-nginx-service \
  --force-new-deployment
    always overwrites

    SEED_WEB_ROOT=always replaces files in the web root on every single start. Any edit made directly on EFS is lost. Use it deliberately, then set it back to ifempty.

    Option B — edit the files on EFS directly

    Launch a small EC2 instance in the same VPC, put it in a security group the EFS group accepts on 2049, and mount the access point:

    sudo dnf install -y amazon-efs-utils
sudo mkdir -p /mnt/site
sudo mount -t efs -o tls,accesspoint=fsap-0a1b2c3d4e5f6a7b8 fs-0a1b2c3d4e5f6a7b8:/ /mnt/site
sudo cp ./index.html /mnt/site/index.html

    The change is live on the next request — sendfile and the open-file cache are both off in nginx/default.conf precisely so nothing stale is served back. No redeploy, no image build.

    14

    When it does not work

    Every one of these has been hit by somebody in this batch.

    SymptomCause and fix
    403 Forbidden on every page The EFS access point POSIX user is not 101:101, so the nginx worker cannot read the document root. Recreate the access point with uid and gid 101.
    404 on every page, log says the web root is empty SEED_WEB_ROOT=never, or the volume was mounted at a different path. The mount point's container path must be exactly /usr/share/nginx/html.
    502 Bad Gateway on /api/tasks Nginx is up but the Node process is not. Read the log lines above the 502 — usually an AWS SDK error at startup.
    AccessDeniedException … dynamodb:Scan Missing or wrong taskRoleArn, or the ARN in the policy does not match the table's region or name.
    ResourceNotFoundException on the table DDB_TABLE or AWS_REGION does not match where you created the table. The table is regional.
    ResourceInitializationError: failed to invoke EFS utils No 2049 rule from the task security group to the EFS security group, or no mount target in the AZ the task landed in.
    Task stuck in PENDING, then CannotPullContainerError Public IP is off in a public subnet, so there is no route to ECR.
    image Manifest does not contain descriptor matching platform An arm64 image built on an M-series Mac. Rebuild with --platform linux/amd64.
    Tasks vanish after a redeploy DDB_ENDPOINT is set in the task definition. Remove it — it points the SDK away from the real service.
    An old page keeps coming back Browser cache, not EFS. Hard-refresh; index.html is served no-cache, static assets with a one-hour cache.
    15

    Tear it down

    In this order. Each command frees something the next one depends on.

    aws ecs update-service --region ap-south-1 \
  --cluster todo-nginx-cluster --service todo-nginx-service --desired-count 0

aws ecs delete-service --region ap-south-1 \
  --cluster todo-nginx-cluster --service todo-nginx-service --force

aws ecs delete-cluster --region ap-south-1 --cluster todo-nginx-cluster

    Then delete, in the console: the EFS access point, every mount target, the file system, the DynamoDB table, the ECR repository, the log group, both security groups and both IAM roles.

    Deleting the file system deletes the website

    And deleting the table deletes every task in it. Neither has a recycle bin unless you took a backup first.
