Deploy a two-container app on ECS Fargate

A click-by-click console runbook. You will put a Node.js frontend and a DynamoDB Local database into one Fargate task, keep the database file on EFS, and prove the data survives when the task is destroyed.

Console only
no CloudFormation
Time
45–60 min
Running cost
~$1.20 / day
Teardown

Runbook

    Your values

    Fill these in once. Every command and field below updates to match.

    Before you start

    The runbook

    1

    Create the ECR repository

    A private registry for your frontend image. Fargate cannot pull from your laptop.

    Amazon ECR›Repositories›Create repository
    FieldValue
    Visibility settingsPrivate
    Repository nametodo-app
    Everything elseleave at defaults

    Choose Create. Copy the repository URI it shows you — it is the value you will paste into the task definition.

    2

    Build and push the image

    The only part of this runbook that is not console clicking.

    The repository page has a View push commands button. Use these instead — they are the same commands with one important change.

    aws ecr get-login-password --region ap-south-1 \
  | docker login --username AWS \
    --password-stdin 111122223333.dkr.ecr.ap-south-1.amazonaws.com
    docker buildx build --platform linux/amd64 --push \
  -t 111122223333.dkr.ecr.ap-south-1.amazonaws.com/todo-app:latest .
    Why not the console's own command

    The console gives you a plain docker build. On an Apple Silicon Mac that produces an arm64 image, and Fargate defaults to x86 — the task then fails with image Manifest does not contain descriptor matching platform. --platform linux/amd64 is what prevents it.

    3

    Create two security groups

    Order matters: the second one refers to the first.

    EC2›Security Groups›Create security group

    First — the group the task itself runs in:

    FieldValue
    Nametodo-task-sg
    VPCyour default VPC
    Inbound ruleCustom TCP · port 3000 · source 0.0.0.0/0
    Outboundleave the default allow-all

    Second — the group on the EFS mount targets:

    FieldValue
    Nametodo-efs-sg
    VPCthe same VPC
    Inbound ruleNFS · port 2049 · source todo-task-sg
    Read the second rule out loud

    The source is a security group, not a CIDR. It says "only something running in the task's security group may mount this file system" — which is tighter than any IP range you could write, and it keeps working when the task's IP changes.

    4

    Create the EFS file system

    This is the disk the database file lives on. Use the Customize flow, not the one-click Create.

    EFS›File systems›Create file system›Customize
    PageSetting
    1 · Nametodo-dynamodb-data
    1 · Storage classRegional
    1 · Automatic backupsUncheck (a POC does not need it, and it bills)
    1 · Throughput modeBursting
    2 · VPCyour default VPC
    2 · Mount targetsRemove the default security group from every row, add todo-efs-sg instead
    3 · File system policyskip

    Create it, then copy the File system ID — it looks like fs-0abc123456789def0. You need it in step 8.

    Do not skip the mount target page

    If a subnet has no mount target, a task that lands in that subnet cannot mount EFS and dies with ResourceInitializationError. Leave a mount target in every AZ whose subnet your service will use.

    5

    Create the EFS access point

    The single most error-prone screen in this runbook. Every number here matters.

    EFS›Access points›Create access point
    FieldValue
    File systemtodo-dynamodb-data
    Namedynamodb-local
    Root directory path/ddbdata
    POSIX user · User ID1000
    POSIX user · Group ID1000
    Root creation · Owner user ID1000
    Root creation · Owner group ID1000
    Root creation · Permissions0755

    Copy the Access point ID — fsap-0abc123456789def0.

    Why 1000, and what happens if you get it wrong

    An access point squashes every file operation to one POSIX user, so that user has to be the one the container actually runs as. Inside the DynamoDB Local image that user is dynamodblocal, uid 1000. Use any other number and the container starts, looks healthy for a few seconds, then loops forever on unable to open database file.

    This number is per-image, not universal. The same lab with PostgreSQL needs 70 for postgres:16-alpine and 999 for the Debian postgres:16.

    Root creation settings only apply once

    They are used the first time /ddbdata is created and never again. If you get the ownership wrong and fix the access point afterwards, point it at a new path — the old directory keeps its old owner.

    6

    Create the log group

    Thirty seconds now, or a task that refuses to start with no visible reason later.

    CloudWatch›Log groups›Create log group
    FieldValue
    Log group name/ecs/todo-ecs-poc
    Retention setting1 week
    Why this is its own step

    The ECS task-definition form creates this group for you. The JSON editor you are about to use does not, and the standard execution role has no permission to create it either. A missing log group stops the task before your code ever runs — and because there is no log group, there is nothing to read.

    7

    Check the task execution role

    Skip this if ecsTaskExecutionRole already exists in your account — most do.

    IAM›Roles›Create role
    FieldValue
    Trusted entity typeAWS service
    Use caseElastic Container Service › Elastic Container Service Task
    Permissions policyAmazonECSTaskExecutionRolePolicy
    Role nameecsTaskExecutionRole
    This role is not your application's identity

    It belongs to the ECS agent, and it does two things: pull the image from ECR and write logs. Your app never uses it. If you later switch to the managed DynamoDB service, you add a task role — a separate thing — for the app itself.

    8

    Create the cluster

    On Fargate a cluster is just a name to group things under. Nothing is provisioned.

    Amazon ECS›Clusters›Create cluster
    FieldValue
    Cluster nametodo-ecs-poc-cluster
    InfrastructureAWS Fargate (serverless) — leave checked
    Monitoring / Tagsleave off
    9

    Create the task definition

    Two containers, one volume. Use the JSON editor — the form cannot express all of this cleanly.

    Amazon ECS›Task definitions›Create new task definition with JSON

    Replace everything in the editor with the following. Three values need editing: the two EFS ids from steps 4 and 5, and your account number if you did not fill it in at the top of this page.

    {
  "family": "todo-ecs-poc",
  "networkMode": "awsvpc",
  "requiresCompatibilities": ["FARGATE"],
  "cpu": "1024",
  "memory": "2048",
  "executionRoleArn": "arn:aws:iam::111122223333:role/ecsTaskExecutionRole",
  "volumes": [
    {
      "name": "dynamodb-data",
      "efsVolumeConfiguration": {
        "fileSystemId": "fs-REPLACE-ME",
        "transitEncryption": "ENABLED",
        "authorizationConfig": { "accessPointId": "fsap-REPLACE-ME" }
      }
    }
  ],
  "containerDefinitions": [
    {
      "name": "database",
      "image": "public.ecr.aws/aws-dynamodb-local/aws-dynamodb-local:latest",
      "essential": true,
      "user": "1000:1000",
      "command": ["-jar","DynamoDBLocal.jar","-sharedDb","-dbPath","/home/dynamodblocal/data"],
      "mountPoints": [
        { "sourceVolume": "dynamodb-data", "containerPath": "/home/dynamodblocal/data" }
      ],
      "logConfiguration": {
        "logDriver": "awslogs",
        "options": {
          "awslogs-group": "/ecs/todo-ecs-poc",
          "awslogs-region": "ap-south-1",
          "awslogs-stream-prefix": "database"
        }
      }
    },
    {
      "name": "frontend",
      "image": "111122223333.dkr.ecr.ap-south-1.amazonaws.com/todo-app:latest",
      "essential": true,
      "portMappings": [{ "containerPort": 3000, "protocol": "tcp" }],
      "environment": [
        { "name": "DDB_ENDPOINT", "value": "http://localhost:8000" },
        { "name": "DDB_TABLE",    "value": "Tasks" },
        { "name": "AWS_REGION",   "value": "ap-south-1" }
      ],
      "dependsOn": [{ "containerName": "database", "condition": "START" }],
      "logConfiguration": {
        "logDriver": "awslogs",
        "options": {
          "awslogs-group": "/ecs/todo-ecs-poc",
          "awslogs-region": "ap-south-1",
          "awslogs-stream-prefix": "frontend"
        }
      }
    }
  ]
}
    The command line is not optional

    The DynamoDB Local image defaults to -inMemory. Leave that in place and everything appears to work — the app runs, tasks save, nothing errors — and then every deploy silently starts from an empty table, with your EFS volume mounted and untouched. -sharedDb matters too: without it the file name is derived from the caller's access key and region, so a change in either quietly opens a different, empty database.

    Four details worth pausing on
    • "user": "1000:1000" matches the access point from step 5.
    • The frontend reaches the database at localhost:8000 because containers in one task share a network namespace.
    • Port 8000 is never published anywhere — the database is unreachable from outside the task.
    • dependsOn ... START only waits for the container to launch. The app retries its connection for about a minute, which covers the rest.
    10

    Create the service

    The service is what keeps one task running and replaces it when it dies.

    Amazon ECS›Clusters›todo-ecs-poc-cluster›Services›Create
    FieldValue
    Compute optionsLaunch type
    Launch typeFARGATE
    Application typeService
    Task definition familytodo-ecs-poc
    Service nametodo-ecs-poc-service
    Desired tasks1
    Deployment options › Min running tasks0%
    Deployment options › Max running tasks100%
    Networking › VPCyour default VPC
    Networking › Subnetstwo public subnets, different AZs
    Networking › Security groupuse existing — todo-task-sg
    Networking › Public IPTurned on
    Load balancingnone
    0% minimum is deliberate

    DynamoDB Local is one SQLite file and only one container may write it. The default 100% minimum would start a replacement task before stopping the old one, and both would fight over the same file. Setting the minimum to 0% stops the old task first. The cost is a few seconds of downtime on every deploy, which is the correct trade for a single-writer database — and it is also why desired count stays at 1.

    Choose Create. The service takes two to four minutes to reach a running task.

    11

    Open the app, then prove EFS works

    Two things to demonstrate: that it runs, and that the data is not inside the container.

    Amazon ECS›Clusters›Tasks›the running task›Networking

    Copy the Public IP and open http://<that-ip>:3000. Add two or three tasks in the UI.

    Now destroy the container the data appears to live in:

    1. Go to the Tasks tab, select the running task, choose Stop.
    2. Watch the service start a replacement — two minutes or so.
    3. Open the new task and copy its Public IP. It will be a different address.
    4. Browse to the new IP on port 3000.
    What you should see

    Your tasks are still there, with the same ids and timestamps. Nothing was written to the container — the replacement mounted the same EFS directory and picked up exactly where the old one left off. Remove EFS from this design and that list comes back empty every single time.

    The IP changes every replacement

    That is normal without a load balancer, and it is the honest reason to put an ALB in front of a real service. For a classroom demo it is a feature: it makes visible that the task really was destroyed and rebuilt.

    12

    Tear it down

    In this order. Each item blocks the one above it.

    ConsoleDelete
    ECS › ServicesUpdate desired tasks to 0, then delete the service
    ECS › Clusterstodo-ecs-poc-cluster
    ECS › Task definitionsDeregister every revision of todo-ecs-poc
    EFS › Access pointsdynamodb-local
    EFS › File systemstodo-dynamodb-data
    EC2 › Security Groupstodo-efs-sg first, then todo-task-sg
    CloudWatch › Log groups/ecs/todo-ecs-poc
    ECR › Repositoriestodo-app
    Deleting the file system deletes the data

    There is no undo and no snapshot unless you turned automatic backups on in step 4. Take a screenshot of the app first if you want the evidence for your notes.

    When it does not work

    Start at ECS › Clusters › Tasks › the stopped task. The Stopped reason field and the per-container Details tab name the cause almost every time. Logs are at CloudWatch › Log groups › /ecs/todo-ecs-poc.

    What you seeWhat it means
    unable to open database file — on repeat, in the database logs The access point uid does not match the image. Step 5 must be 1000. Fixing the access point is not enough if /ddbdata already exists — point it at a new path.
    Task list is empty after every deploy, no errors anywhere The command override in step 9 is missing, so DynamoDB Local is running -inMemory and ignoring your EFS volume entirely.
    ResourceInitializationError: failed to invoke EFS utils The task cannot reach the file system. Check that todo-efs-sg allows 2049 from todo-task-sg, and that a mount target exists in the AZ the task landed in.
    CannotPullContainerError Either the public IP is off (a task in a public subnet needs one to reach ECR), or the execution role is missing, or the image is the wrong architecture — see step 2.
    Task goes straight to STOPPED with no logs at all The log group does not exist. Go back to step 6.
    Waiting for DynamoDB (attempt N)… forever in the frontend log The database container is not listening. Confirm DDB_ENDPOINT is http://localhost:8000, and read the database container's own log stream.
    Two tasks running, both unhealthy, after a redeploy Minimum running tasks is above 0%, so two containers are fighting over one SQLite file. Step 10.

    What this deliberately leaves out

    No load balancer, so the address changes; no private subnets, so the task is directly reachable; and a database container rather than the managed DynamoDB service. That last one is the honest limit of this lab — DynamoDB Local exists to teach the API without a bill, and running it on EFS is how you give a Fargate task any durable disk at all.

    The production shape of this app is smaller, not bigger: point it at real DynamoDB and the database container, the EFS file system, the access point, the mount targets and their security group all disappear. What replaces them is one task role granting the app access to its table.
