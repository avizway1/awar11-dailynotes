Google built this for their internal systems. This project's initial name is B0RD. Later they renamed it to OMEGA.

In 2014, Google handed their project to CNCF as an open source project. They named it Kubernetes. 

CNCF : Cloud Native Computing Foundation : this CNCF manages a lot of open source projects. Anyone can contribute to these projects: you, me, anyone. Generally CNCF will have two types of projects:
1. Graduated : fully matured project that has a large number of organisations at the production level. 
2. Incubated : still a lot of feature enhancement is going on. We may face some feature limitations if we use it in real environments. 

K8s architecture:
1. Control plane : Brain of K8s
2. Data plane : hands of K8s


1. CONTROL PLANE COMPONENTS:

1.1 kube-apiserver / apiserver : 
- This is the front door of Kubernetes. It’s a single point of contact for communicating with our Kubernetes cluster.
- If we want to deploy a workload, view an existing workload, or delete anything, we communicate with the kube API server using kubectl. 
-kube api server validates the configuration.

The API server is a component of the Kubernetes control plane that exposes the Kubernetes API. The API server is the front end for the Kubernetes control plane.

kubectl apply -f file1.yaml				--> 10 pods
kubectl apply -f file2.yaml
kubectl create ns myapp

1.2 etcd (etc distributed) : (traditional Linux has all its configuration in /etc so they picked the same for Kubernetes workloads that work across nodes. They added distributed)

- etcd contains all the information about the Kubernetes cluster: its configuration, its workload 
- In etcd all the information is stored in key-value pairs.
- You can treat etcd as a Kubernetes full-fledged database. 
- It stores the current and desired state of the cluster. Example: you created a workload with 5 pods. Now you want to increase it to 10. The information is stored here. 
- If we lose access to etcd, our cluster state is lost. 
- STRICT COMMINICATION : No component in Kubernetes speaks to etcd directly except the API server. Every other component, (i.e the scheduler, control manager, and cloud control manager) goes through the API server to read and write data. 

1.3 kube-scheduler : 
- It looks for an available worker node to run our workload based on node resource utilisation, like CPU or memory.
- When it wants to run the pod, it will pick the best node to run our workload based on a scoring mechanism.

1.4 kube-controller manager : 
- kube-controller manager acts as a supervisor. 
- It monitors etcd and ensures our application's current state matches the desired state. 
- If we ask for 10 replicas but only 5 are running, then it sent instructions to the kube scheduler to pick the best node to run the workload. 
- Kube controller manager runs in the background in a loop. It always checks with etcd via the API server and makes sure the desired state matches the actual state. 

1.5 cloud-controller-manager : 
- this will extend Kubernetes capabilities to cloud resources to utilise components like IAM roles, VPC, load balancer, and EFS. 

2 DATA PLANE / WORKER NODES : 

2.1 kubelet : 
- kubelet is an agent that runs in every worker node. 
- kubelet listens to all control plane instructions and ensures our pods are running and healthy. 
- If any container goes down, kubelet will restart it automatically. **

2.2 kube-proxy : 
- kube-proxy is a networking component. This also runs on every node, similar to kubelet. 
- Kube-proxy assigns an IP address to every pod created on this worker node. 
- The primary purpose of Kube-proxy is to handle network communications inside and outside of the cluster. 
- Kube-proxy ensures that traffic reaches the right container. 

2.3 Container Runtime : 
- Container runtime is responsible for pulling images and running containers. 
- Kubernetes uses containerd or CRI-O as a runtime from version 1.24. Earlier it used Docker. 
- Kubelet sends instructions to the container runtime to pull the image and start the container inside the pod.

EKS : Elastic Kubernetes Service : it is an AWS fully managed Kubernetes service. 
AWS takes care of all the control plane components. High availability and fault tolerance are purely AWS's responsibility. 
- In the backend AWS stores k8s configuration at least six copies across three availability zones. 

** AWS costs: 10 cents per hour for managing this control plane.  (0.10 $)

Limitations with managed clusters:
- We cannot access control plane nodes.
- We don't get the option to see where these control plane nodes are running. 


Amazon EC2 managed node group : 
- AWS automatically provisions and configures managed instances 
- We need to handle the instance type selection (right sizing).
- On our behalf AWS will manage the patching and scaling of these instances.

Amazon EC2 Self managed Node group : 
- We manually need to provision and configure the ec2 instances.
- We need to handle the scaling, OS patching and security patching.

EKS Automode: AWS automatically picks the required configuration of an EC2 instance. We can combine on-demand and spot instances. Also it has capabilities to scale with various configurations. 
* Compared with other options, costs very very less for these EKS auto-mode clusters. 

AWS Fargate : this is a serverless option: no worker nodes to manage. Our pods are going to run directly. This is less used compared to other options because of its resource limitations, and compliance issues.

pod : Pod is the smallest deployable unit in Kubernetes. A pod contains a container. 
- We cannot directly run a container in Kubernetes. 
- A pod is a wrapper around the container. 

Question: can a pod contain multiple containers? 
Ans: we can have multiple containers but we always have one primary container that does the actual job. The other container is the helper container. We call that helper container a sidecar container. 

One important point: both containers can't use the same port. Both run on two different ports.

Resource limiting : we can define how much memory or CPU should be allocated to the container. If we don't define this value, however much is available on our underlying host container will be available to the container as well. 
problem : one container may consume all the underlying host resources. other containers end up with resource constrain.

Requests : guaranteed minimum : minimum CPU or memory Kubernetes guarantees to allocate to the container.
limits: hard ceiling : the maximum CPU or memory a container is permitted to consume. This option prevents a single container from consuming all the resources.

Service : service acts as a stable network abstraction over an ephemeral group of pods. Pods will be regularly created and destroyed based on the load so a pod IP address will be changed. Pod IP addresses are not constant. 

1. ClusterIP (Default) : Cluster IP exposes the service within an internal IP address. 

- Works only within the cluster. 
- Cluster IP creates a stable IP address. 
- Treat this component as an internal load balancer or intercom system. 
- 90% of the microservices run with cluster IP only as we don't want to expose it to the outer world. 

To test the output on our local laptop, we need to perform port forward. 

kubectl port-forward svc/cip-service 8080:80

DNS / Service name formats:
FQDN : <service-name> (cip-service)
Cross Namespace: <service-name>.<namespace>  (cip-service.default)


kubectl describe svc cip-service

Endpoints: 192.168.16.236:80,192.168.48.137:80,192.168.9.248:80, 192.168.50.43

Connect to any of the pod..

curl http://cip-service

2. NodePort : NodePort builds on top of ClusterIP by opening a static port on every node's IP address. 
Port Range : 30,000 - 32,767

- Node port has a specific range to map at the node level.
- We can choose a port manually. If we don't choose, the system will pick one automatically in the given port range.
- We can deliver output to the outside world by using the node IP address.
- At the instance security group level we need to open the random port or node port range we configured.

- NodePort is a superset of ClusterIP. We can use this for local developments only not for production level. 

** Make sure to open the NodePort Configured / autogenerated IP address at instance Security group level to get the output.


3. LoadBalancer : with the help of Cloud Control Manager, Kubernetes will create a load balancer in our AWS environment. It creates a classic load balancer. 

** AWS stopped supporting the classic load balancer so we don't get any security updates and we don't get any support from AWS. 
- In lower environments, to verify our output very quickly, we consider this but we don't run our production workload by using this load balancer. 


4. ExternalName : it doesn't route traffic or it won't use a label selector to target pods. Instead it maps an internal Kubernetes service name to an external DNS name. 

- it simply creates a DNS alias.
- It doesn't create a ClusterIP / Proxy or it wont use Loadbalancer.
